## Blockers

### 1. Raw JSON Metadata & Diagnostic Leak to Chat on Empty or Non-Text Turn
- **File & Line**: [`pkg/bridge/channels_relay.go:100-112`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/bridge/channels_relay.go#L100-L112)
- **Failure mode in practice**: `AnswerChannelMessage` runs `s.agent().CreateConversation(args)`. For `cliBackend`, `CreateConversation` returns a JSON object containing keys: `agent`, `status`, `conversation_id`, `model`, `response`, `duration_seconds`, `num_turns`, `usage`, `elapsed_seconds`. When the agent executes tool calls or completes a turn without emitting text in `response` (e.g. `response == ""`), none of the guessed keys (`response`, `text`, `message`) contain non-empty string content. Line 108 evaluates `strings.TrimSpace(raw) == ""` as false because `raw` is the full serialized JSON payload. Line 111 then returns `raw, nil`. The entire internal JSON structure—including token usage, internal conversation IDs, and elapsed execution timing—is posted directly into the user's WhatsApp or Telegram chat. The same leak occurs if the backend returns error JSON lacking those three keys.
- **Smallest correct change**: If `json.Unmarshal` succeeds on `raw`, never fall back to returning `raw`. If none of the recognized keys yield a non-empty string, return an error:
  ```go
  var parsed map[string]interface{}
  if json.Unmarshal([]byte(raw), &parsed) == nil {
  	for _, key := range []string{"response", "text", "message"} {
  		if value, ok := parsed[key].(string); ok && strings.TrimSpace(value) != "" {
  			return value, nil
  		}
  	}
  	return "", fmt.Errorf("agent completed turn with no text response")
  }
  ```

### 2. `AnswerChannelMessage` Broken for Desktop App (`AgentApp`) Backend
- **File & Line**: [`pkg/bridge/channels_relay.go:96-107`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/bridge/channels_relay.go#L96-L107), [`pkg/bridge/lead.go:245-253`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/bridge/lead.go#L245-L253)
- **Failure mode in practice**: When `s.agent()` resolves to `appBackend` (Antigravity 2.0 desktop app), `LeadHandler.CreateConversation` is purely an asynchronous dispatch tool: it types the prompt into the Lexical editor via CDP, clicks send, and returns:
  ```json
  {
    "status": "dispatched",
    "conversation_id": "conv-...",
    "prompt": "...",
    "submission_step": 0,
    "message": "Conversation initiated in local Antigravity 2.0. Call 'antigravity_lead_await_response' to receive the agent's completed response and artifacts."
  }
  ```
  `AnswerChannelMessage` checks for keys `["response", "text", "message"]`, matches the `"message"` key, and immediately returns the instruction string `"Conversation initiated in local Antigravity 2.0. Call 'antigravity_lead_await_response'..."` as the reply to WhatsApp/Telegram! It never invokes `AwaitResponse`. The channel sender receives internal prompt dispatch instructions, and the real response generated by Antigravity 2.0 is never delivered.
- **Smallest correct change**: In `AnswerChannelMessage`, when the backend is `AgentApp` or returns `"status": "dispatched"`, immediately call `s.agent().AwaitResponse(map[string]interface{}{"conversation_id": convID, "timeout_seconds": 120})` and extract the text from the completed response preview.

### 4. `DefaultProject` is Completely Ignored by Both Backends in `CreateConversation`
- **File & Line**: [`pkg/bridge/channels_relay.go:94`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/bridge/channels_relay.go#L94), [`pkg/bridge/cli.go:455-465, 349`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/bridge/cli.go#L455-L465), [`pkg/bridge/lead.go:75-80`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/bridge/lead.go#L75-L80)
- **Failure mode in practice**: `AnswerChannelMessage` passes `args["cwd"] = project`. However:
  1. In `pkg/bridge/cli.go`, `CLIHandler.CreateConversation` extracts only `prompt`, `model`, `timeout_seconds`, and `effort`. It never reads `cwd`. In `runTurn`, `cmd.Dir = h.workDir()`, which pins the process to `h.cwd` or daemon `os.Getwd()`.
  2. In `pkg/bridge/lead.go`, `LeadHandler.CreateConversation` extracts only `prompt` and `title`. It never touches `cwd`.
  As a result, `DefaultProject` is inert in both backends. Inbound channel messages execute in whatever working directory the daemon process was launched from.
- **Smallest correct change**: In `CLIHandler.CreateConversation`, extract `cwd := argString(args, "cwd", "")` and pass it to `runTurn`, which sets `cmd.Dir = cwd` when non-empty. For `LeadHandler`, reject or log that workspace switching is unsupported.

### 5. Contention on `__pending__` Run Lock Causes Concurrent Inbound Turns to Fail Instantly and Permanently Drop Messages
- **File & Line**: [`pkg/webgui/server.go:7406, 7488`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/webgui/server.go#L7406), [`pkg/bridge/cli.go:372-378`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/bridge/cli.go#L372-L378)
- **Failure mode in practice**: When multiple messages arrive simultaneously (or WhatsApp delivers a multi-message webhook array), `server.go` launches concurrent goroutines: `go s.relayWhatsApp(...)` / `go s.relayTelegram(...)`. Each invokes `CreateConversation`. In `cli.go`:
  ```go
  key := conversationID
  if key == "" {
  	key = "__pending__"
  }
  h.mu.Lock()
  if _, busy := h.runs[key]; busy {
  	h.mu.Unlock()
  	return nil, fmt.Errorf("a turn is already running for conversation %s; wait for it or stop it first", conversationID)
  }
  ```
  Because all new conversations start with `conversationID == ""`, the first goroutine locks `__pending__`. Every other concurrent goroutine instantly fails with `"a turn is already running..."`. In `relayTelegram` and `relayWhatsApp`, this error is merely logged with `log.Printf` and the goroutines exit. Because `MarkMessageSeen` already marked their IDs as seen before dispatch, the dropped messages will never be retried or processed. Senders receive no response and no error.
- **Smallest correct change**: Serialize channel turn execution through a channel queue or mutex in the relay service so inbound messages queue and execute sequentially instead of crashing against the `__pending__` lock.

## Should Fix

### 7. Telegram Bot Token in URL Query String Exposes Master Secret via Logs and Proxies
- **File & Line**: [`pkg/webgui/server.go:7474`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/webgui/server.go#L7474), [`pkg/webgui/auth_middleware.go:110-113`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/webgui/auth_middleware.go#L110-L113)
- **Failure mode in practice**: The Telegram webhook verifies requests using `r.URL.Query().Get("token") == cfg.Telegram.BotToken`. The bot token is the master administrative secret for the bot. URLs and query parameters are logged in plain text by reverse proxies (Caddy, Nginx, Cloudflare), CDN tunnels, server access logs, and browser histories. Anyone with access to proxy logs obtains full bot control. Furthermore, standard `!=` string comparison is vulnerable to timing attacks. Telegram's official standard sends a separate `secret_token` in the `X-Telegram-Bot-Api-Secret-Token` HTTP header.
- **Smallest correct change**: Check `r.Header.Get("X-Telegram-Bot-Api-Secret-Token")` using `subtle.ConstantTimeCompare`, maintaining query parameter fallback only for legacy setups.

### 8. In-Memory Deduplication (`seenIDs`) Lost on Daemon Restart and O(N) Iteration Under Lock
- **File & Line**: [`pkg/bridge/channels_relay.go:62-86`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/bridge/channels_relay.go#L62-L86)
- **Failure mode in practice**: `seenIDs` is held in an unpersisted package-level map. When the daemon restarts or crashes, all history is lost. WhatsApp Cloud API retries webhooks for up to 7 days on transient connection issues. Following a daemon restart, retried messages are treated as new, re-running expensive agent turns and duplicating workspace modifications. Additionally, `MarkMessageSeen` performs an O(N) loop over all entries to prune TTL expired items on every single message while holding `seenMu`.
- **Smallest correct change**: Persist seen message IDs to `filepath.Join(core.GetConfigDir(), "channel_seen_ids.json")` (or append to a simple journal), load it on startup, and prune expired entries on a background ticker (e.g. hourly) instead of on every incoming message.

### 10. Silent Error Swallowing Leaves Sender Waiting Indefinitely
- **File & Line**: [`pkg/webgui/server.go:7421-7428, 7496-7503`](file:///mnt/Data/Projects/Antigravity%20Swiss%20Knife/pkg/webgui/server.go#L7421-L7428)

  }

## Attacks on the 8 Brief Questions

1. **AnswerChannelMessage JSON Parsing & Fallback Leaks**:
   - `CLIHandler.CreateConversation` returns a JSON string with metadata keys and `response`. If `response` is empty or parsing yields no matches, the fallback `return raw, nil` sends the raw JSON object to the chat.
   - For `LeadHandler.CreateConversation`, it returns an async dispatch acknowledgment with `"message": "Conversation initiated..."`. `AnswerChannelMessage` mistakes this for the turn answer, transmitting prompt instructions to chat and never awaiting the actual turn.
2. **Dedupe Map Persistence**:
   - In-memory is unacceptable because WhatsApp retries for up to 7 days upon delivery failure. Restarts re-execute costly turns and modify project files.
   - Smallest fix: Persist seen IDs and expiry timestamps in a lightweight JSON file in `core.GetConfigDir()`.
3. **Relay Concurrency Limit & Turn Leaks**:
   - 5 concurrent messages immediately clash on `CLIHandler.runs["__pending__"]`. 1 succeeds and 4 fail immediately with a busy error, permanently dropping all 4 messages.
   - In `LeadHandler`, 5 concurrent messages initiate competing CDP injections into the single Lexical DOM editor.
   - Turns lack an overall cancellation context.
4. **Telegram Token in Query String**:
   - Indefensible: the bot token is the master administrative secret. Reverse proxies, CDNs, and log collectors record URL query strings in plain text.
   - Standard practice is the `X-Telegram-Bot-Api-Secret-Token` header set via `setWebhook`.
5. **DefaultProject as cwd Validation**:
   - `args["cwd"]` is completely ignored by both `CLIHandler` and `LeadHandler`. Turns run in the daemon's working directory.
   - If wired directly, relative or missing paths cause `chdir` failures. Needs absolute path and existence validation.
6. **Removed AgentACP Config Fallback**:
   - Silently collapses to `""` ("Bridge default") in UI and config without warning.
   - More severely, `ChannelsConfig.AgentBackend` is never consulted by `AnswerChannelMessage`, making the UI setting completely inert.
7. **Immediate 200 Webhook Ack vs Failure Feedback**:
   - Immediate 200 ACK is required to avoid webhook retry floods from Meta/Telegram.
   - However, silent swallowing on background failure leaves the user waiting forever. When `AnswerChannelMessage` fails, an error message must be dispatched back to the sender.
8. **Inbound Telegram/Discord Completeness & UI Clarity**:
   - Discord inbound is completely unimplemented despite UI claiming full bidirectional support.
   - Telegram long polling is completely unimplemented despite UI defaulting to it and claiming "Long Polling Active".
   - `AllowedChatIDs` and `AllowedNumbers` whitelists are never checked by the webhook handlers.
